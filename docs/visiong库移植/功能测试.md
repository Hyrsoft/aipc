基于你在 功能测试.md 里列的 3 个现象，我对当前代码的分析结论如下。

**问题 1 分析**
1. “disconnectWS is not defined” 是前端真实代码错误，不是后端部署失败  
定位：重连函数里调用了不存在的方法。  
- 调用点：App.svelte、App.svelte  
- 实际定义的方法名是：App.svelte、App.svelte、App.svelte、App.svelte  
- 触发链：部署时先切 VisionG，再调用重连；重连抛异常后被 deploy 的 catch 捕获，最终日志显示“部署失败: disconnectWS is not defined”。对应流程在 App.svelte 和 App.svelte。

2. 从其他 VisionG 工程切到 yolov5 报 “必须定义 run()” 是脚本契约不一致  
- 运行时明确要求 run()：见 visiong_producer.cpp  
- 但工程创建默认模板写的是 process()：见 http.cpp  
- 你仓库里的示例项目也有 process 风格（不是 run 风格）：见 yolov5_detection.py  
所以这个报错是“当前运行时契约”和“项目模板/示例契约”混用导致的必现问题。

**问题 2 分析（VisionG 二次部署后大量 Failed to send frame to VENC）**
高概率是 Venc 生命周期与脚本 cleanup 的资源回收时序冲突，不是单点语法问题：

1. VisionG 编码线程只做了 ScopedUser 引用计数  
- 线程入口持有用户计数： visiong_producer.cpp

2. 线程结束后只会调用 releaseUser，默认不会自动释放 VENC 通道  
- releaseUser 只是减计数： VencManager.cpp  
- 真正释放通道需要显式调用 releaseVencIfUnused： VencManager.cpp

3. UpdateCode 会先执行 old cleanup，再起新脚本  
- 流程在 visiong_producer.cpp 附近  
- 你的日志里 old cleanup 已释放 Camera/全局资源，而后新线程编码发送失败，对应 VENC 发送失败位置是 VencManagerEncode.cpp

这解释了“二次部署后连续 send frame 失败”的症状：逻辑上像是 VENC 状态未完全与底层资源回收保持一致。

**问题 3 分析（切回 SimpleIPC 后各分发通道收不到帧）**
这是一个非常关键的状态机问题，和“部署失败后 running 变 false”强相关：

1. UpdateCode 失败时不会重启脚本线程  
- 先把 running 置 false 并 join，再加载代码；失败则不重启： visiong_producer.cpp

2. 模式切换时只在 was_running=true 才启动新生产者  
- was_running 取旧 producer 的 IsRunning： media_manager.cpp  
- 只有 was_running 才 Start： media_manager.cpp

所以当 VisionG 因脚本错误进入 not running 状态后，再切回 SimpleIPC，会出现“模式切了但没启动采集/编码线程”，结果就是所有通道无帧。  
这与你描述的“第一次切 VisionG 后再回 SimpleIPC 出 bug”高度一致。

**补充结论**
- 你看到的第 1 和第 3 个问题，实际上互相放大：前端重连函数命名错误会制造“部署失败”表象；脚本契约不一致会把 VisionG 置为 not running；随后切回 SimpleIPC 因状态机条件不满足不自动 start，最终表现为全链路无帧。
- 第 2 个问题是独立的运行时资源生命周期风险，主要在 VENC/Camera 二次部署回收与重建路径。
