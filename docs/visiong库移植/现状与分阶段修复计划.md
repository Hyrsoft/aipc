# VisionG 集成现状与分阶段修复计划

## 1. 背景与目标

当前 AIPC 需要将 VisionG 集成为 Edge AI 执行层，同时保持现有媒体链路（VENC 编码 + RTSP/WebRTC/WebSocket 分发）稳定可用。项目已经尝试过三条路径：

- 直接使用 VisionG C++ API：灵活性不足，改动成本高。
- 嵌入式 Python：灵活，但当前出现切换/部署时崩溃。
- Python 子进程 IPC：理论可隔离，但在嵌入式端对未压缩帧传递成本过高，且会冲击现有流媒体主链路。

本方案结论：继续采用嵌入式 Python，但必须收紧生命周期管理与帧回传职责边界。

## 2. 当前实现现状（基于源码）

### 2.1 模式切换主流程是冷切换

AIPC 当前通过 `MediaManager::SwitchMode` 执行冷切换：`Stop -> Deinit -> 销毁旧实例 -> 创建新实例 -> Init -> 重注册消费者 -> Start`。

现状意义：
- 大方向正确，符合嵌入式设备上“确定性优先”的原则。
- 问题不在切换框架本身，而在 VisionGProducer 内部运行时边界。

### 2.2 VisionGProducer 使用嵌入式 Python 运行时

当前 VisionGProducer 的关键链路：
- 初始化 `PythonRuntime`。
- `LoadCode` 中执行 `py::exec(code, globals)` 并绑定 `process/init/cleanup`。
- `FrameLoop` 中持续调用 `ProcessFrame`，拿到 `ImageBuffer` 后送入 `VencManager` 编码，再分发。

现状意义：
- 这条链路满足“Python 处理后回到 C++ 编码分发”的基础闭环。
- 但实现层面仍有竞态与契约不统一问题。

### 2.3 Python 默认项目仍是“自采集 + 自推理”风格

以默认项目 `assets/python_projects/yolov5_detection.py` 为例，脚本在 `init` 中创建 `Camera/NPU`，`process` 中自行 `snapshot + infer + draw`。

现状意义：
- Python 端仍在承担采集主控职责。
- 与“C++ 驱动帧循环、Python 只做处理”的目标不一致。

### 2.4 API 语义反映出职责下沉到 Python

当前 pipeline 状态接口在 VisionG 模式下提示分辨率由 Python 工程控制。

现状意义：
- 说明系统控制面正在被 Python 脚本侵入。
- 不利于统一调度、稳定运维和可回归验证。

## 3. 现阶段主要问题分层

### 3.1 层 A：生命周期与并发安全问题（最高优先）

症状：
- 切换或 deploy 时出现段错误风险。
- 问题集中在 `LoadCode -> py::exec` 与运行中替换代码路径。

根因：
- `UpdateCode` 与帧处理路径未形成系统级“安全点门控”。
- runtime 对象在检查与使用之间存在竞态窗口。

影响：
- 稳定性不可预测。
- 难以通过简单重试规避。

### 3.2 层 B：职责边界错位（架构一致性问题）

症状：
- Python 脚本自行创建 Camera、自行拉帧、自行推理。
- C++ 对采集节奏和生命周期控制不足。

根因：
- 脚本契约仍沿用“脚本主控”模式，而非“C++ 主控回调”模式。

影响：
- 切换路径变复杂。
- 与 AIPC 既有编码/分发架构耦合不良。

### 3.3 层 C：吞吐与画质策略不足（性能问题）

症状：
- 编码码率策略固定化（当前固定值）。
- 分发和编码链路缺少明确背压策略。

根因：
- VisionG 模式补齐了功能，但未补齐工业化流控。

影响：
- 高分辨率下画质与延迟波动。
- 慢消费者可能拖累整体链路。

## 4. 风险矩阵（现状）

- 高风险：LoadCode/deploy 与 frame loop 并发导致的崩溃窗口。
- 高风险：runtime 检查与使用分离导致的时序问题。
- 中风险：Python 自采集模型导致资源控制权分散。
- 中风险：编码参数策略与分辨率不匹配。
- 中风险：缺少背压导致延迟与丢帧不可控。
- 低风险：接口语义与目标架构不一致，长期会增加维护成本。

## 5. 分阶段修复计划

### Phase A：稳定性止血（先保证不崩）

目标：把切换和 deploy 从“偶发崩溃”收敛为“可预测失败”。

任务：
- 统一 `UpdateCode/ProcessFrame/Stop/Deinit` 的安全边界，确保 deploy 只在安全点生效。
- 消除 runtime 检查-使用分离窗口，保证 `FrameLoop` 使用 runtime 的一致性。
- 为 `LoadCode` 建立分层错误归类（`exec` 失败、`init` 失败、签名错误），增强定位能力。

验收：
- 连续 50+ 次 `simple_ipc <-> visiong` 切换无服务退出。
- deploy 成功/失败均不导致主服务崩溃。
- `/api/status` 与 `/api/python/status` 在失败场景下仍可响应。

### Phase B：架构对齐（C++ 主控，Python 纯处理）

目标：回到 AIPC 既有媒体主链路，避免 Python 接管系统控制面。

任务：
- 统一 Python 脚本契约为“输入帧 -> 输出帧”，禁止脚本内自建采集主循环。
- VisionGProducer 固化为 C++ 驱动帧循环：取帧 -> Python 处理 -> VENC -> 分发。
- 收回关键控制面语义（如分辨率/帧率）到 C++ 配置管理。

验收：
- 默认项目不创建 Camera 也可正常推理并输出流。
- 切换后配置行为与 SimpleIPC 模式保持一致性预期。

### Phase C：吞吐与质量优化（稳定后提效）

目标：控制延迟抖动与画质波动，提升工程可运维性。

任务：
- 码率策略按分辨率/帧率动态配置，替代固定值。
- 引入有界队列与丢帧策略，补齐背压。
- 增加性能观测指标（帧处理耗时、编码失败率、队列积压）。

验收：
- 480p/720p/1080p 三档下均有可接受的延迟与画质表现。
- 慢消费者存在时系统可退化运行，不出现持续性卡死。

## 6. 回归验证清单

### 6.1 功能回归

- 模式切换成功率：simple_ipc 与 visiong 双向切换。
- Python deploy 成功率：最小脚本到完整脚本逐步恢复。
- 编码分发可用性：RTSP/WebRTC/WebSocket 均可持续输出。

### 6.2 稳定性回归

- 长时运行（至少数小时）不崩溃。
- 高频 deploy 与切换组合压测。
- 错误脚本、模型缺失、加载失败场景下服务可自恢复或可诊断。

### 6.3 可观测性回归

- 日志覆盖关键路径：switch、PythonInit、LoadCode、frame loop、encode。
- 失败日志可直接归类，不需要二次猜测。

## 7. 方案边界（明确不做）

- 不采用 Python 子进程承担主编码与主分发。
- 不让 Python 脚本接管 AIPC 的流媒体控制主逻辑。
- 不在当前阶段追求“完全无停顿热切换”，先确保稳定与可回归。

## 8. 实施顺序建议

- 先做 Phase A，解决“会不会崩”。
- 再做 Phase B，解决“架构是否一致”。
- 最后做 Phase C，解决“性能是否达标”。

该顺序可最大化降低联调成本，并保证每一阶段均可独立验收。
